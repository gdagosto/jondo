# Cazacabezas and Heroes server-plugin migration

Baseline `00e8dfb4` (`modding api start`). Paths are repository-relative. Commit `00e8dfb4` added client DLL distribution and nested settings. Gameplay still runs in the server assembly.

## Shared settings, distribution and authentication

- `Jondo.Unity.Server/ServerSettings.cs` (`Current`, `Load`, `Read`) reads `config/server_settings.json` for the running process. `Read` imports legacy flat fields when the corresponding nested object is absent or null. `Jondo.Unity.Server/UI/ServerSettingsView.cs` shows each mod’s gameplay controls when its DLL is available. Settings edits take effect after restart. DLL order and gameplay enablement are independent.
- The local, untracked `config/server_settings.json` uses legacy fields. It resolves to Cazacabezas disabled with a 15-minute window and 30-minute rest, and Heroes enabled with two followers and map reload off. `ClientMods` is absent, so the default order applies. These are checkout settings and may differ from a running server’s startup snapshot.
- `Cazacabezas/Cazacabezas.csproj` and `Heroes/Heroes.csproj` target `net6.0` and reference MelonLoader and game IL2CPP assemblies. `GuardarMod` copies builds to `mods/Cazacabezas.dll` and `mods/Heroes.dll`. `DesplegarMod` also copies to the installed client’s `Mods/` when present unless `SkipModDeploy=true`.
- `Jondo.Unity.Core/Paths.cs` (`ClientModsDirectory`) resolves `<root>/mods`. `ServerSettings.ClientMods` defaults to `JondoFix.dll`, `Cazacabezas.dll`, `Heroes.dll` in that order. `Jondo.Unity.Server/Network/ClientModCatalog.cs` (`ListAvailable`, `CreateManifest`, `OpenDownload`) discovers DLLs, emits configured available entries in order with name, byte size and SHA-256, skips missing files, excludes links, rejects invalid/duplicate names and enforces contract limits. `Jondo.Unity.Server/Network/ControlApi.cs` (`Mods`) and `Jondo.Unity.Server/Network/HaapiServer.cs` (`ServeClientModAsync`) serve unauthenticated `GET /api/mods` and `GET /api/mods/{name}`. Downloads require an exact configured name. `Jondo.Unity.Contract/ClientModManifest.cs` caps manifests at 128 entries and each DLL at 128 MiB. An empty order serves an empty manifest.
- `Jondo.Unity.Launcher/Setup/ClientModSync.cs` (`Prepare`, `Activate`) uses matching bundled DLLs or verifies downloads into a SHA-256 cache. `Jondo.Unity.Launcher/UI/LauncherPreferences.cs` (`TrustedModManifest`, `TrustModManifest`) stores approval per host for the manifest fingerprint. A changed previously approved manifest or an unrecognized DLL requires approval. `JondoModLoader/ServerModsPlugin.cs` (`OnPreModsLoaded`, `LoadApprovedManifest`) reads `JONDO_CLIENT_MOD_MANIFEST`, verifies cached bytes and loads in manifest order in MelonLoader. `Jondo.Unity.Launcher/LauncherService.cs` (`LaunchClient`, `InstallMod`, `ShippedModPath`) retains bundled install for compatible legacy launches after a 404 from a host with no saved approval. `Jondo.Unity.Mcp/GameClients.cs` still installs bundled copies directly.
- `Cazacabezas/CazacabezasMod.cs` (`CazacabezasMod`, F7) and `Heroes/HeroesMod.cs` (`HeroesMod`, Ctrl+Tab and Tab switching) POST JSON to `http://127.0.0.1:8888/api/`. Both read `JONDO_PLAYER_TOKEN` with `JONDO_CONTROL_TOKEN` as fallback. All gameplay routes below go through `ControlApi.Responder` → `ConSesion`, which resolves the body’s `token` via `Jondo.Unity.Server/Network/ClientLaunchRegistry.cs` (`ResolveToken`, registry then DB `LauncherToken` and `GameToken`). Invalid tokens receive `401 sesion`. The route cases have no per-route verb check. `ControlApi.InTheWorld` finds the authenticated account’s in-world character with an active selection.

## Cazacabezas

- **Settings** — `CazacabezasModSettings.Enabled=true`, `HuntWindowMinutes=15`, `RestMinutes=30`. Legacy aliases `HeadHunters`, `HeadHuntWindowMinutes`, `HeadHuntRestMinutes`. `HeadHunts.Window` and `Rest` enforce minima of 1 and 0 minutes respectively.
- **Client work** — `CazacabezasMod.OnUpdate` polls status every 2 seconds with its window or an active hunt, otherwise every 6 seconds, with error backoff. It adds an alignment-tab button and displays the hunt tracker. `OnInitializeMelon` leaves the UI idle without a player token.
- **Routes** — `Jondo.Unity.Server/Network/ControlApiHeadHunts.cs` maps `/api/headhunts/{status,board,take,abandon}` to `HeadHuntStatus`, `HeadHuntBoard`, `HeadHuntTake`, `HeadHuntAbandon`. All require `InTheWorld` or return `409 world`. `take` reads target character ID from `target`. The hunter always comes from the resolved session.
- **Storage and clock** — `Jondo.Unity.Server/Managers/HeadHunts.cs` (`Load`, `Ensure`, `Keep`, `Drop`) lazily loads/creates tables in `DatabaseManager.WorldConnectionString` (`bases/world.db` by default). `HeadHunters` is keyed by `CharacterId` with `Chapeuvepes`, `Kills`, `Survivals`, `Failures`, `Streak`, `LockedUntilMs`. `HeadHuntOrders` is keyed by `Hunter` with `Target`, `TakenMs`, `OpenUntilMs`, `RestUntilMs`. Both participants are character IDs and timestamps use Unix milliseconds. Reload clears open state and keeps the later of the saved open/rest deadlines. `Jondo.Unity.Server/Program.cs` (`StartServicesAndWaitAsync`) runs non-overlapping `TickAsync` every five seconds and disposes the timer on shutdown. The tick checks `On`, opens/closes/expires orders and sends sightings.

## Heroes

- **Settings** — `HeroesModSettings.Enabled=true`, `MaxHeroes=7`, `ReloadMapOnSwitch=false`. Legacy aliases `HeroMode`, `HeroesMax`, `HeroSwitchReloadsMap`. `Heroes.Max` clamps the follower count to `1..Heroes.Most` (7).
- **Client work** — `HeroesMod.OnInitializeMelon` installs client UI hooks when a token is available. `OnUpdate` polls the list every 3 seconds with a window or group panel, otherwise every 8 seconds, with auth-error backoff. The group panel uses server state for character controls, life and portraits.
- **Routes** — `Jondo.Unity.Server/Network/ControlApiHeroes.cs` serves `/api/heroes/{list,connect,disconnect,portrait,quests,autopass,loot,sheet,switch,create,name,preview}`. `HeroesPortrait` checks account ownership. `HeroesName` and `HeroesPreview` need a token only. The remaining routes use `InTheWorld` and derive the master from it. `id` denotes a character and connected-hero operations check the master relationship. `HeroesCreate` calls `CharacterCreationHandler.Make` before attempting `Heroes.Connect`, so a character can be created without joining the active group. `HeroesSwitch` supports both immediate and deferred selection.
- **Storage and lifetime** — `Jondo.Unity.Server/Managers/Heroes.cs` holds `_byMaster`, `_byHero`, `_lootTo`, `_questSyncOff`, `_questLags`, `_partyHeld`, `_switchTo` and `_leftBehind` in process. Membership, auto-pass, loot routing and quest-sharing preferences have no server-side persistence. Short-lived switch and regroup state is keyed by account ID. Normal character data is persisted via `Jondo.Unity.Server/Managers/DatabaseManager.cs` (`SaveCurrentCharacter`, `Characters`, `CharacterItems`, `CharacterQuests`, `CharacterAchievements`, `CharacterSpellChoices`, `CharacterSpellBar`). `Jondo.Unity.Server/Managers/DungeonKeyring.cs` writes `CharacterKeyring` by character/dungeon/week usage. `Jondo.Unity.Server/Managers/DungeonProgress.cs` writes `CharacterDungeonProgress` by character/dungeon and `CharacterDungeonHubWins` by character/dungeon/room. `Jondo.Unity.Server/Managers/ZaapDiscoveries.cs` writes `CharacterZaapDiscoveries` by character/map. The client stores `Heroes.PanelX` and `Heroes.PanelY` in `UserData/MelonPreferences.cfg`. `HeroesList` calls `HeroPortraits.Warm` for its in-process cache. Hero lifecycle is driven by requests and gameplay, with switch/regroup expiry checked on access.

## Runtime loading and implementation order

- `Jondo.Unity.Server/Jondo.Unity.Server.csproj` targets `net10.0` with `SelfContained=false`, `PublishSingleFile=true` and `IncludeNativeLibrariesForSelfExtract=true`. The RID defaults to `NETCoreSdkRuntimeIdentifier`. Checked-in server publish paths specify neither trimming nor Native AOT. The framework-dependent apphost requires .NET 10 on the host. `DeployServer` copies only the apphost to the root unless `SkipRootDeploy=true`.
- `.github/workflows/release.yml` publishes the Windows apphost and explicitly targets `linux-x64` for Linux. `.github/scripts/New-JondoRelease.ps1` packages `mods/` and `JondoModLoader/JondoModLoader.dll`. `Dockerfile` publishes `linux-x64`, uses a .NET 10 runtime image and copies the apphost and `mods/` to `/app`. There is no server-plugin loader or server-plugin artifact in these paths. Plan for an explicit server-plugin directory and dependency resolution against the host’s shared types. Verify loose DLL loading and dependency identity in both published apphosts and the container, since publish bundles the host’s managed assemblies and the current deploy target stages only the executable.
- Start with startup/shutdown, routes and package layout. Move Cazacabezas next, keeping admission decisions synchronous with their callers and settlement after the fight result. For Heroes, establish ownership and teardown first, then party/presence, dungeon planning/payment, fight control and reward settlement. Keep client routes and saved character IDs stable across the cutover.

## Existing test entry points

Run from the repository root with the .NET 10 SDK. Gameplay fixtures use `bases/world.db` from `datos/world.zip` and create test characters there.

```sh
dotnet test Jondo.Unity.Tests/Jondo.Unity.Tests.csproj --filter "FullyQualifiedName~HeadHuntTests|FullyQualifiedName~World.HeroesTests|FullyQualifiedName~DungeonHeroesTests|FullyQualifiedName~HeroProbeTests|FullyQualifiedName~HeroAchievementsTests|FullyQualifiedName~ZaapDiscoveryTests|FullyQualifiedName~ClientModSyncTests|FullyQualifiedName~ModInstallTests"
dotnet test Jondo.Unity.Server.Tests/Jondo.Unity.Server.Tests.csproj --filter "FullyQualifiedName~ClientModCatalogTests|FullyQualifiedName~ServerSettingsWindowTests|FullyQualifiedName~HeroSwitchSyncTests|FullyQualifiedName~AchievementStateTests|FullyQualifiedName~GuildRosterTests"
```

- `Jondo.Unity.Tests/World/HeadHuntTests.cs` covers eligibility/opening, holds/rest, wins/losses, session auth and currency trades. `Jondo.Unity.Tests/World/HeroesTests.cs` covers ownership, switch/regroup, party, presence, quests, trade, control and solo fights. `Jondo.Unity.Tests/World/DungeonHeroesTests.cs` covers the key planner and shortfalls. `Jondo.Unity.Tests/Combat/HeroProbeTests.cs`, `Jondo.Unity.Tests/Sessions/HeroAchievementsTests.cs` and `Jondo.Unity.Tests/Movement/ZaapDiscoveryTests.cs` cover fight control/bar, achievement ownership and zaap discovery.
- `Jondo.Unity.Tests/Launcher/ClientModSyncTests.cs` and `Jondo.Unity.Tests/Launcher/ModInstallTests.cs` cover approval, cache reuse, corrupt downloads and bundled install. `Jondo.Unity.Server.Tests/ClientModCatalogTests.cs` and `Jondo.Unity.Server.Tests/ServerSettingsWindowTests.cs` cover catalog order, filename checks, settings migration and restart behavior. `Jondo.Unity.Server.Tests/HeroSwitchSyncTests.cs`, `Jondo.Unity.Server.Tests/AchievementStateTests.cs` and `Jondo.Unity.Server.Tests/GuildRosterTests.cs` cover switch state, hero achievement delivery and socketless online status. `RunTestsBeforePublish` in the server project runs general, server and protocol suites by default, with narrower filters for `JondoProtocolTarget=3.8.1.2`.

## Unverified behavior

The current code and tests do not establish how a future server plugin will load, resolve dependencies or stop in each published layout. Live MelonLoader/IL2CPP behavior across client versions and hosts, crash/restart recovery of a live hunt, and recovery after a partial Heroes key debit or interrupted handover are unverified end to end.
